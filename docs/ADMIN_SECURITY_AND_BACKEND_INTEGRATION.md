# NEXVION AI — Admin Security Architecture & Backend Integration Specification

## 1. Executive Summary & Security Boundary Definition

This document outlines the architectural boundaries, security specifications, and backend integration requirements for the NEXVION AI Administration Portal.

> [!CRITICAL]
> **Fundamental Security Principle**:
> Frontend role-based checks, hidden buttons, and route view guards are **UI affordances only** designed for user experience and operator workflow orientation. **Frontend permissions do NOT protect data and do NOT constitute a security boundary.**

---

## 2. Core Security Mandates

### 2.1. Authentication Architecture
- **Firebase Authentication** must be the sole identity provider.
- Admin sessions must be verified via signed JWT ID tokens issued by Firebase Authentication.
- Multi-factor authentication (MFA/TOTP) should be enforced for all administrative and directorate roles (`Owner`, `Super Admin`, `Finance Manager`).
- Session timeouts and token refresh intervals must be strictly enforced.

### 2.2. Server-Side Authorization & Custom Claims
- **Role assignments and capabilities must reside in Firebase Auth Custom Claims** or securely cached Firestore session documents validated on every backend request.
- The 8 administrative roles (`Owner`, `Super Admin`, `Content Manager`, `Student Manager`, `Finance Manager`, `Communications Manager`, `Support Manager`, `Analyst`) must have strict server-side capability definitions.
- Every API endpoint, Cloud Function, and Firestore listener must independently authorize incoming claims against the operation's capability requirements before executing any data reads or mutations.

### 2.3. Cloud Firestore Security Rules
- All client-side direct database access via Firebase SDKs must be governed by declarative, granular Firestore Security Rules.
- Rules must validate:
  1. Authenticated user ID matches `request.auth.uid`.
  2. Administrative claims exist: `request.auth.token.role in ['Owner', 'Super Admin', ...]`.
  3. Strict schema validation: Invariant checks such as **maximum batch capacity capped at 30 students**.
  4. Write restrictions: Non-privileged users (e.g. students or unauthorized roles) must receive unconditional `permission-denied` on administrative collections (`/admins`, `/roles`, `/auditLogs`, `/platformSettings`, `/payments`).

### 2.4. Server-Side Payment Verification
- Client-side payment flows and status changes (`Pending`, `Paid`, `Refunded`) must **never** be accepted directly from frontend requests.
- Payment webhooks from processors (Stripe, Razorpay, PhonePe) must be validated using cryptographic webhook signatures inside isolated Cloud Functions.
- Refunds, fee overrides, and invoice receipts must be processed through backend ledger microservices.

### 2.5. Server-Side Notification Dispatches
- Real-time broadcasts, SMS, email triggers, and Firebase Cloud Messaging (FCM) pushes must be dispatched exclusively by trusted backend functions or queue workers.
- The frontend client only posts an author-reviewed dispatch request; server-side workers sanitize message bodies, query recipient cohorts, enforce rate limits, and record dispatch telemetry.

### 2.6. Server-Side Tamper-Proof Audit Logging
- Server-side audit logging must be automatically generated by Firestore triggers (`onCreate`, `onUpdate`, `onDelete`) and backend API middleware.
- Client applications cannot directly write or manipulate `/auditLogs` documents.
- Audit records must capture:
  - Timestamp (server timestamp `request.time`)
  - Authenticated admin UID & email
  - Action name & classification
  - Entity collection & target identifier
  - Pre-state snapshot & post-state diff
  - Origin IP address, request ID, and User-Agent
- Audit log retention policies must be immutably enforced.

### 2.7. Secrets & Credential Isolation
- **No secrets, API private keys, service account credentials, webhook signing secrets, or private certificates may exist in frontend source code or client bundles.**
- All sensitive credentials must reside in Google Cloud Secret Manager or encrypted environment variables accessible only to cloud runtimes.

## 3. Data Provider Migration Strategy

The frontend architecture is fully isolated behind the typed repository interface layer (`NexvionServices` / `NexvionAdminData`):
- `courseRepository`
- `tierRepository`
- `batchRepository` (Enforces 30-student cohort hard-cap invariant)
- `studentRepository`
- `enrollmentRepository`
- `contentRepository`
- `projectRepository`
- `announcementsRepository`
- `notificationRepository`
- `paymentRepository`
- `certificateRepository`
- `supportRepository`
- `analyticsRepository`
- `adminRepository`
- `roleRepository`
- `auditRepository`
- `settingsRepository`

When backend services are provisioned, each repository's internal data source will simply transition from local storage providers to Firestore SDK / Cloud Functions client calls, with zero disruption to the UI component architecture.
